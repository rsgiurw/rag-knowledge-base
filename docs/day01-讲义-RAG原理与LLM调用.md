# Day 1 讲义 · RAG 原理与 LLM API 调用

> 学习目标：搞懂 RAG 的完整链路和三个地基概念（token 与参数 / embedding 与余弦相似度 / 流式输出）。
> 对应脚本：`backend/scripts/01_hello_llm.py`、`02_hello_embedding.py`。

## 一、为什么需要 RAG

大模型有三个天生的问题，靠模型自身解决不了：

1. **知识截止**：训练完成之后的世界它不知道（新制度、新文档）；
2. **私有知识缺失**：公司内部制度、客户资料根本不在训练数据里；
3. **幻觉**：不知道也会一本正经地编。

RAG（Retrieval-Augmented Generation，检索增强生成）的思路非常朴素：
**别让模型凭记忆答题，让它开卷考试**——先从你的文档里把相关内容检索出来，塞进 prompt，再让模型"看着资料回答"。

## 二、RAG 完整链路（背下来，面试要画图）

```
【离线索引：一次性/文档更新时】
  文档 → 解析(PDF/Word→纯文本) → 分块(chunking) → 向量化(embedding) → 存入向量库

【在线问答：每次提问】
  问题 → 向量化 → 在向量库里找 top-k 最相似的块 → 拼装 Prompt(资料+问题) → LLM 生成 → 带引用回答
```

本项目 Week 1 做的就是这条链路的每一环，全部手写；Week 2 优化"检索"这一环。

## 三、概念 1：LLM API 与 token

- **token**：模型处理文本的最小单位。英文约 1 词 ≈ 1.3 token；中文约 1 字 ≈ 1~2 token（不同分词器不同）。**计费和上下文窗口都按 token 算**——这就是为什么 RAG 只塞 top-k 相关块而不是整本文档。
- **messages 角色体系**：
  - `system`：设定行为和约束，优先级最高（我们的"只根据资料回答"就放这里）；
  - `user` / `assistant`：对话历史，多轮对话就是把它们都带上。
- **temperature**（0~1 或 0~2）：控制随机性。本质是采样时对概率分布"削峰填谷"——低温让高概率词更容易被选（稳定、适合知识问答），高温让分布更平（多样、适合创意）。
- 一次调用的成本 ≈ (输入 token + 输出 token) × 单价。省钱的两个方向：**检索得准（少塞资料）+ prompt 复用**。这是 Week 2 优化的话题。

## 四、概念 2：Embedding 与余弦相似度

- **embedding 模型**把一段文本映射成一个固定长度的向量（本项目用智谱 `embedding-3`，2048 维）。训练目标让"语义相近的文本，向量方向也相近"。
- **余弦相似度**：`cos = A·B / (|A|·|B|)`，只看方向不看长度，值域 [-1, 1]。
  - 直觉：把每个维度想成一个"语义特征轴"，两个向量在某轴上同号且大，说明它们在这个语义上相近。
  - 为什么不用欧氏距离？向量长度受文本长度等因素影响（长文本向量模可能更大），方向更能代表"语义本身"。这个问题的标准答案要在理解上面这句话后用自己的话说出来。
- **向量检索 = 语义匹配**："年假怎么算" 和 "工龄满 10 年每年 10 天" 没有共同关键词，但向量很近——这是关键词检索做不到的。
- **它的短板**：对精确词不敏感（型号、人名、编号），Week 2 用 BM25 关键词检索 + 混合检索来补。

## 五、概念 3：流式输出（SSE）

- 本质是一条**长连接 HTTP 响应**：服务器不一次发完，而是把回答切成小块，每块用 `data: {...}\n\n` 帧推给客户端，以 `data: [DONE]` 结束。这个协议叫 Server-Sent Events。
- 为什么需要：生成 500 token 要十几秒，等全部生成完再返回，用户体验极差。流式让首字响应出现在 1 秒内。
- Day 4 我们会在自己的 FastAPI 后端把 SSE 转发给 React 前端——今天先在脚本里看原始形态。
